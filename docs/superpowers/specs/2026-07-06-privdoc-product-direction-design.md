# PrivDoc 产品方向设计

## 目标

PrivDoc 要成为本地敏感文档管理工具，服务那种真实存在、格式混乱、但每天都离不开的 `secrets.txt`。

它要保留纯文本的自由度，同时加上一层更安全的操作界面：识别敏感条目、默认隐藏密钥、精确复制字段、保存修改历史，并且除非用户主动编辑，否则不改动原文。

## 产品定位

PrivDoc 是本地敏感 txt 的智能外壳。

它不是密码管理器。它的竞争对手不是 1Password、KeePassXC 或浏览器自动填充。它真正替代的是一份很长的本地 txt / Markdown，里面混着服务器密码、云服务 Key、开发者账号、收款账号、公司开票资料、SSH 信息、1Panel 日志和各种敏感运维备注。

第一性原理是：

> 保留 txt 的自由度，把敏感信息的使用动作从“看见、选中、复制”改成“识别、隐藏、精确复制”。

原文永远是真相。智能解析只生成查看态的操作模型，不把用户强行迁移到新的结构化存储格式。

## 非目标

PrivDoc 不应该把这些能力作为核心方向：

- 浏览器自动填充。
- 云同步。
- 团队共享。
- 对齐传统密码管理器功能清单。
- 强制模板。
- 自动重写用户原文。
- 自动合并重复条目。
- 新保存默认使用 Keychain。
- 做成服务器管理面板。

这些边界的意义是防止产品漂移成密码管理器、云笔记或运维控制台。

## 目标用户

第一目标用户是已经有本地敏感 txt 的个人开发者或 solo operator。

这份文档通常不干净，里面可能有：

- 云服务 Key。
- 邮箱账号和密码。
- Apple / Google 等开发者账号。
- SSH 命令和 root 密码。
- 1Panel 安装日志。
- VPN 或 X-UI 面板地址。
- 公司开票和银行资料。
- 重复记录。
- 标题下面直接跟着的裸密钥行。
- 分隔线、复制来的日志和随手写的备注。

这个用户重视透明和控制。他愿意把文件加密保存，但不希望 App 静默整理、重写或改变原始文档。

## 优先级

已确认的产品优先级是：

1. 复制准。
2. 不暴露。
3. 改不坏。
4. 找得快。

这个顺序很重要。只有先安全识别并复制正确的敏感值，快速搜索才有意义。

## 核心对象模型

PrivDoc 应该从“字段优先”升级为“条目优先”。

```text
Document 原文
  -> Entry 条目
      -> Item 可操作项
```

`Document` 是加密保存的原始文本，也是唯一真相。

`Entry` 是查看态解析出来的一块敏感条目，例如：

- `阿里云OSS`
- `Google Developer`
- `正式服务器`
- `Example Service`
- `SSH / 192.0.2.106`
- `1Panel / 203.0.113.75`

`Item` 是条目里的可操作值，例如：

- URL
- 邮箱
- 用户名
- 密码
- API Key
- KeySecret
- SSH 主机
- SSH 用户
- IP
- 端口
- 面板用户
- 面板密码
- 公司开票字段
- 备注

Entry 和 Item 都是从原文解析出来的查看态对象，不是强制保存格式。

## 解析原则

解析器必须保守。

错误暴露比少识别更严重。如果 PrivDoc 无法判断一个长的不透明字符串是不是密钥，应默认隐藏。如果 PrivDoc 无法可靠判断一段文本该怎么结构化，应保留原文并给出 best-effort 查看态。

解析过程不能静默重写原文。

## 条目识别

Entry 识别应该利用真实乱文本里的天然信号：

- 空行。
- 长分隔线，例如 `-----` 或 `————`。
- 单独一行的中文或英文短标题。
- 服务名，例如 `阿里云OSS`、`Twilio`、`Google Developer`、`VPN`。
- 服务器标题，例如 `正式服务器`、`测试服务器`、`国内公司服务器主机`。
- SSH 命令行，例如 `ssh root@192.0.2.106`。
- 1Panel 日志标记，例如 `[1Panel ... Log]`。

短的独立行可以被当成条目标题，即使它不是 Markdown 标题。

如果 1Panel 日志前面没有明显标题，PrivDoc 可以从 host 或 IP 生成标题，例如 `1Panel / 203.0.113.75`。

## 可操作项识别

每个 Entry 内部，PrivDoc 应识别这些 Item：

- `http://` 或 `https://` 开头的 URL。
- 邮箱地址。
- `ssh user@host` 格式的 SSH 命令。
- IP 地址。
- 使用 `:`、`：` 或 `=` 的字段行。
- 中文服务字段，例如 `外部地址`、`内部地址`、`面板用户`、`面板密码`、`账号`、`密码`。
- 云服务字段，例如 `Key`、`KeySecret`、`AccessKey`、`Secret`、`Token`。
- 标题或账号后面的裸长字符串。
- 1Panel 安装日志字段。

当前字段解析器仍然有价值，但它应该成为 Entry 解析内部的一层能力，而不是整个产品模型。

## 敏感度规则

默认隐藏：

- 字段名包含 `密码`、`KeySecret`、`Secret`、`Token`、`Cookie`、`恢复码`、`private key`、`client_secret` 或类似密钥词。
- 云服务 `Key` 值。
- 裸长不透明字符串。
- 1Panel 面板密码。
- SSH 命令后紧跟的裸字符串，推断为 SSH 密码。
- 面板 URL 里的随机路径 token。

默认可见：

- 条目标题。
- 邮箱地址。
- 用户名。
- 主机名。
- IP。
- 端口。
- 普通公开 URL。
- 公司名称、地址、开户行、发票抬头等业务资料。

URL 需要特殊处理：

- `https://developer.apple.com/` 这类普通 URL 可以完整显示。
- `http://198.51.100.42:9443/random-token` 这类面板 URL 应显示 host 和端口，隐藏路径 token。
- 复制被脱敏的面板 URL 时，应复制完整原始 URL。

搜索不应包含隐藏值。搜索可以包含标题、字段名、可见账号、host、IP 和端口。

## 纠错模型

乱文本解析不可能一次完美，所以纠错必须轻。

用户应能右键教 PrivDoc：

- 这个字段当密钥。
- 这个字段当普通文本。
- 这一行当条目标题。
- 这一行归到上一个条目。

当纠错代表用户习惯时，可以沉淀成全局解析规则。默认不把这些纠错写进加密文档，因为原文应保持不变。

## 产品路线图

### Phase 1：Smart View

Smart View 是下一版核心。

目标：打开现有混乱敏感文档后，不要求用户清理原文，也能安全、准确地复制常用值。

范围：

- 把原文解析成 Entry。
- 在 Entry 内解析 Item。
- 默认隐藏密钥。
- 面板 URL 显示脱敏版本，但复制完整值。
- 可操作项支持双击复制。
- 保留剪贴板清理策略。
- 搜索避开隐藏值。
- 增加右键纠错：密钥 / 普通文本 / 标题。

验收例子：

- `阿里云OSS` 能识别 `Key` 和 `KeySecret`，两者都隐藏且可复制。
- `Google Developer` 能识别邮箱为账号，后续裸字符串为隐藏值。
- `ssh root@192.0.2.106` 能变成 SSH 条目，拆出用户 `root`、主机 `192.0.2.106`，下一行裸字符串识别为隐藏密码。
- 1Panel 日志能识别外部地址、内部地址、面板用户、面板密码。
- 面板 URL 视觉上隐藏随机路径 token，但复制完整 URL。
- 公司开票资料不会因为包含账号、地址等信息被误判成密码。

### Phase 2：Safe Editing

目标：让用户敢把真实敏感 txt 迁进 PrivDoc，因为改错能恢复。

范围：

- 编辑态继续是原文编辑。
- 每次有意义的修改保存为版本。
- diff 从纯字段级升级到尽可能按 Entry / Item 展示。
- 历史预览继续脱敏。
- 恢复版本前明确提示会覆盖当前原文。
- 支持替换密钥时不必先显示旧密钥。

### Phase 3：Import Assist

目标：帮助用户把旧 txt 放进 PrivDoc，但不要求先整理格式。

范围：

- 打开或粘贴原始 txt。
- 显示解析预览。
- 标出疑似标题、疑似密钥、疑似账号、URL 和重复条目。
- 用户可在第一次保存前纠正解析。
- 保存时仍保留原文。
- 后续可以生成建议整理版，但不能自动替换原文。

### Phase 4：Fast Access

目标：当文档变大后，用户能快速拿到某个值。

范围：

- 全局快捷搜索窗口。
- 搜索标题、账号、host、IP、端口和字段名。
- 回车复制选中结果的默认项。
- 常用条目 pin。
- 最近复制目标只记录字段名，不保存 secret 值。

## 安全边界

PrivDoc 应尽量避免意外暴露：

- 查看态隐藏密钥。
- 搜索排除隐藏值。
- 历史预览脱敏。
- 面板 URL token 视觉隐藏。
- 剪贴板清理明确且可预测。
- 锁定时尽量清除 PrivDoc 自己写入的剪贴板内容。

PrivDoc 也不能制造虚假的安全感：

- App 保护的是加密文件和解锁后的 UI 行为，不代表能覆盖所有系统级暴露路径。
- 剪贴板管理器、录屏、系统日志和内存抓取是额外风险。
- Argon2id、更完整的内存清理、正式签名仍属于后续安全工作。

## 实现形态

下一阶段实现不应重写整个 App。

合理路径是：

- 继续让 `VaultPayload.currentDocument` 保存原文。
- 在现有行解析器旁边新增 Entry / Item 解析器。
- 复用已有字段检测逻辑。
- 保留全局解析规则，并扩展标题/条目相关规则。
- 查看态以 Entry 为主要渲染对象。
- 编辑态继续是原文 + 解析预览。
- 加密、历史、剪贴板能力继续作为已有基础。

## 成功标准

Smart View 成功的标准是：一份真实混乱的敏感 txt 不需要手动清理，用户也能从查看层安全复制大多数常用值。

针对当前真实文档形态，PrivDoc 应能处理：

- 云服务 Key。
- 开发者账号。
- 邮箱账号。
- SSH 记录。
- 1Panel 日志。
- 带 secret 路径 token 的面板 URL。
- 公司开票资料。
- 重复服务区块。

第一阶段目标不是完美解析，而是：

> 不修改原文的前提下，让至少 80% 的常见复制动作比直接使用 raw txt 更安全、更准确。

## 产品风险

- 解析过度激进会降低信任。
- 解析过度保守会让 Smart View 太像当前字段解析器。
- 如果文档有很多小块，Entry 卡片可能显得很重。
- 全局规则如果太隐式，用户会不理解为什么解析结果变化。
- 重复检测很诱人，但自动合并风险高，应保持为后续辅助功能。

## 当前决策

推进 Smart View 产品方向：

- 原文保持不变。
- Entry-first 解析成为主查看模型。
- 密钥隐藏和精确复制是最高优先级。
- 导入清理和快速搜索放到后续阶段。
